**Scope:** Whole-repo, read-only structural audit. No code, schema, config, or dependency changes were made.

> This audit was generated by walking the live tree (`shared/schema/`, `server/`, `client/src/`, `migrations/`, `docs/`, `e2e/`, `scripts/`, `.replit`, `package.json`, `tsconfig.json`, `vite.config.ts`, `drizzle.config.ts`) and cross-referencing route registrations, RBAC tables, and migration history. ## 1. Project Overview

**SmartManageAI** is a multi-tenant SaaS construction-management platform. A single Node/Express app serves both a React SPA (Vite) and a JSON API. Each customer is an `organizations` row with branded routing, feature flags, and subscription tier. The platform spans estimating, takeoff, project management, financials, payroll, CRM, hiring, safety/compliance, vendor portals, dispatch, AI assistance, and an AASHTOWare/DOT heavy-civil module.

- `client/src/components/` has **195 components** at the top level alongside 40+ subfolders — partial migration to subfolders (not finished).
- The repo root holds **17 historical audit/dump files** (`FULL_CODE_AUDIT.md`, `4_12_26_platform_audit.md`, `TFR_*` dumps, etc.), some 100s of KB each, plus stale build artifacts (`new-index-Bfh7U-X8.js`, `new-vendor-*.js`, `dist/`, `node_modules/`). These are not used at runtime but pollute the working tree.
- Two whitespace-named files exist at root: `'Simplification Proposal '` (0 B) and `'SmartManageAI System Feature Bible'` (0 B). Likely orphans.

## 4. Data Layer

### 4.1 Schema files

| File | Tables | LOC |
|---|---:|---:|
| `shared/schema/core.ts` | 19 | 878 |
| `shared/schema/operations.ts` | 129 | 4,068 |
| `shared/schema/crm-upgrade.ts` | 9 | 238 |
| `shared/schema/features.ts` | **375** | **11,535** |
| `shared/schema/enums.ts` | 0 (enums only) | 984 |
| **Total** | **532** | **~17,700** |

`shared/schema/features.ts` alone is the single most concentrated risk in the repo. With 375 unrelated tables in one file, every `git blame`, code review, and Drizzle type recompile pays the price. Split is overdue.

### 4.2 Indexes & FKs

- `index(...)` declarations: **1,111** across schema files — strong index coverage, especially `features.ts` (807 indexes for 375 tables ≈ 2.15 per table average).
- `.references(...)` declarations: **1,306** — heavy relational usage.
- `onDelete: "cascade"`: present in all four schema files.
- `onDelete: "restrict"`: only in `features.ts` — most of the remainder of the schema relies on cascade or default-no-action. Some FK inconsistency between modules.

**FK gap noted in the project task list**: "Add the missing document FK link in our heavy-civil schema definitions" — confirms a known unresolved gap in `features.ts` heavy-civil tables.

### 4.3 Storage layer

Two competing patterns coexist:

1. **`server/storage.ts`** (2,218 lines, 85 KB) — a flat module of free-standing functions (`createExecutiveDigest`, `getLatestExecutiveDigest`, etc.), not an `IStorage` interface. The fullstack-js convention in this repo's skill assumes `IStorage` but the actual code does not implement it.
2. **Direct Drizzle `db` calls** scattered throughout 250+ `*Routes.ts` files. Most route handlers do their own queries, bypassing `storage.ts` entirely.

This means the "storage interface" is largely fictional. There is no single chokepoint for cross-tenant safety, soft-delete, or audit hooks.

### 4.4 Migrations

- 103 SQL files in `migrations/`, going from `0000_add_passkey_credentials.sql` through `0076_ai_takeoff_scale_mismatch.sql`.
- **Filename collisions exist** (e.g. four files named `0044_*`, four `0045_*`, three `0046_*`, four `0057_*`). Drizzle-Kit dedupes by hash, but human readability suffers and "what shipped first" is hard to reconstruct.
- A `drizzle/` directory holds additional helper SQL plus a `runStartupMigrations` utility (`server/utils/runStartupMigrations.ts`) imported by `server/index.ts:32`. Two parallel migration paths is a maintenance hazard.
- Schema drift is auto-detected at startup (per `replit.md`). Good practice, but production rollouts of mismatched schema can still surface as runtime errors.

### 4.5 N+1 / pagination risk

- Server-side `limit:` literals appear only in a handful of files (mostly Box/folder listings in `integrationRoutes.ts`). Most list endpoints do not paginate.
- `replit.md` claims "opt-in pagination", but this is not enforced uniformly. Pages such as `client/src/pages/crm.tsx` (2,651 lines) load whole datasets via TanStack Query without explicit limit/offset in many query keys.

### 5.3 How credentials are sourced

A single registry: `process.env.*`. There is **no central typed env loader / Zod-validated config object** — env vars are read inline from across the server, which creates drift and makes "which envs does this app actually need to start?" hard to answer.

`server/index.ts` does enforce a few critical ones at startup: `SESSION_SECRET` (line ~57 of `auth.ts`) — fail-fast pattern. Most others fall back silently or simply disable a feature when missing.

### 5.4 SSRF / outbound-call hardening

The project task list explicitly calls out "Block AI document loaders from fetching arbitrary URLs (SSRF hardening)" — a known unresolved risk. AI document fetchers in `server/aiDocumentRoutes.ts` and similar route files appear to fetch user-supplied URLs without an allowlist.

## 10. Authentication & Authorization

### 10.1 AuthN

- **Mechanism**: JWT signed with `SESSION_SECRET` (aliased as `JWT_SECRET` in `server/auth.ts:64`), 7-day expiry, in `auth_token` httpOnly cookie. Token includes `tokenVersion` for revocation.
- **Sessions**: stateless JWT; `connect-pg-simple` is installed but the active code uses cookie-only JWT.
- **Password**: bcrypt cost 10 (`hashPassword`).
- **Account lockout**: `failedLoginAttempts` + `lockedUntil` columns on `users`.
- **2FA / TOTP**: `otplib` installed; UI present.
- **Passkeys / WebAuthn**: `@simplewebauthn/*` 13 + `passkey_credentials` table (migration `0000`); `passkeyRoutes.ts`.
- **OAuth**: Google, Apple, Microsoft, plus social-only providers (LinkedIn, Twitter, TikTok, YouTube, Pinterest, Facebook) for posting.
- **SSO/SAML**: `@node-saml/node-saml` 5 + `ssoRoutes.ts` + `enterprise-settings` UI.
- **Auth cache**: in-memory map with 8-second TTL (`server/auth.ts:11–53`) — not invalidated on cluster nodes; safe only for single-instance deploys.

### 10.2 AuthZ

- **Roles in code**: 8 (`SUPER_ADMIN`, `ADMIN`, `HUSTLER`, `MANAGER`, `SUPERINTENDENT`, `ESTIMATOR`, `FIELD_WORKER`, `VENDOR`) per `client/src/lib/rbac.ts:31`.
- **Roles in docs/feature bible**: 18, including specialized variants (Office Manager, Project Engineer, Dispatcher, Safety Manager, HR Manager, Equipment Manager, Procurement Manager, Maintenance Manager, Sales, Marketing, Hourly Employee). These are referenced as `roleLabel`/`role` overrides but not all enforced as first-class enum values — **doc/code drift**.
- **Feature permission keys**: 73+ defined as `FeaturePermissionKey` union in `server/auth.ts:355–415`. Persisted per-user in `userDashboardPermissions`.
- **Plan/feature gating**: `server/middleware/requireFeature.ts` checks org subscription entitlements via `services/featureAccess.ts`.

### 10.3 Middleware ladder (in order, `server/routes.ts`)

```
opsRoutes               → unauthenticated ops/health endpoints
authMiddleware          → populates req.user (bypass if no cookie)
requireActiveOrganization → blocks suspended orgs
apiLimiter              → 1000 req/15min per user/IP
[per-route] requireRole / requireFeaturePermission / requireRoleOrFeature
[per-route] requireFeature (subscription gate)
```

### 10.4 Tenant isolation

The audit flagged **per-router** counts of organization filtering and `requireRole` calls (highest: `vendorRoutes.ts` 76, `laborRateRoutes.ts` 64, `hiringRoutes.ts` 51). Most routers do filter by `req.user.organizationId`, but it is not centrally enforced — there is no Drizzle-level tenant policy, no Postgres RLS, and no shared "scoped DB" wrapper. A bug in any one of 270 route files can leak cross-tenant data. The known open task "Tighten cross-tenant safety on the Compliance view" confirms this risk has materialized at least once.

There is dedicated test coverage at `server/__tests__/org-isolation/org-isolation.test.ts` and `npm run test:isolation`, which is good but only covers a slice.

### 10.5 CSRF

- Double-submit cookie pattern in `server/csrf.ts` (`csrf_token` cookie + `x-csrf-token` header). Validated for non-GET methods.
- Exemptions (lines 26–60): `/api/auth/login`, `/api/auth/register`, `/api/auth/forgot-password`, `/api/auth/reset-password`, `/api/stripe/webhook`, `/api/takeoff/stylus-telemetry/batch`, `/api/webhooks/*`, `/api/dev/*` (dev-seed), `/api/auth/google`, `/api/auth/apple`, `/api/auth/passkey`, `/api/email/oauth`, `/api/integrations/connections`, `/api/portal/auth`, `/api/public/*`, `/api/v1/public/*`, and S3 multipart `PUT`. Each exemption is justified inline, but the surface is wide — every exemption must rely on its own auth model.

## 11. Error Handling & Logging

### 11.1 Logger

- `server/utils/logger.ts` provides `logDebug/logInfo/logWarn/logError` with structured JSON output in production and human-readable lines in dev. Includes context fields (`userId`, `organizationId`, `correlationId`, `requestId`, `method`, `path`).
- **221 raw `console.log/warn/error/info` calls** remain across `server/*.ts` — the structured logger is not consistently adopted. Files like `server/ai/orchestrator.ts` log via `console.log('🤖 …')` directly.

### 11.2 Error capture

- `server/services/errorLogService.ts` persists `errorLogs` rows.
- `server/index.ts` registers global `uncaughtException` and `unhandledRejection` handlers that both log and persist.
- Sentry is *referenced* via `SENTRY_DSN` env var, but no `@sentry/*` package is in `dependencies` — Sentry integration is partial / aspirational.

### 11.3 Per-route error handling

- `server/responseHelper.ts` exposes `successResponse` / `errorResponse` and `safeJsonParse` (with a 10 MB guard). Adoption is uneven — many handlers `res.status(500).json({error: ...})` inline.
- 3,278 `} catch` blocks across `server/*.ts`. Many swallow the error (`.catch(() => {})`) — this is by design in some scheduler hooks but deserves per-call review (especially `persistErrorLog().catch(() => {})` in `server/index.ts:43,55`).
- There is **no central Express error-handler middleware** registered. Errors that escape a try/catch propagate to the default Express handler (HTML response).

### 11.4 Correlation / request IDs

- Logger schema supports `correlationId` and `requestId`, but no middleware was found that assigns them per request. Cross-service tracing is therefore weak.

## 12. Performance & Scalability

### 12.1 Caching

- In-memory `authUserCache` with 8-second TTL (`server/auth.ts:10–53`). Bounded at 2,000 entries.
- `server/cache.ts` exists; used by some hot paths. Without Redis or a shared cache, multi-instance autoscale will see thrash.
- TanStack Query handles client-side caching well.

### 12.2 Pagination

- The "opt-in pagination" claim in `replit.md` is not generally enforced. Most list endpoints (`/api/projects`, `/api/bids`, `/api/crm/...`) return all matching rows.
- The CRM page (`crm.tsx`, 2,651 lines) and several admin tables (`admin-transcript-backfill.tsx`, 6,360 lines) load full datasets. Known slow paths.

### 12.3 N+1

- Audit scripts in `scripts/audit-*.mjs` exist for several N+1-adjacent patterns (audit-logger userId, catch binding, next-without-param), suggesting prior cleanup effort.
- Direct evidence of N+1 was not exhaustively searched, but the pattern of "route handler does its own queries" without a service layer makes N+1 inevitable in places.

### 12.4 Rate limiting

- Four tiers in `server/rateLimiter.ts`: `authLimiter` (15/15min), `sensitiveLimiter` (100/15min), `apiLimiter` (1000/15min), `exportLimiter` (20/15min). Plus a `feedbackLimiter` referenced elsewhere.
- `apiLimiter` is bypassed in dev seed mode.
- Limits are stored in-memory by default — for autoscale this means **per-instance limits, not per-user globally**. A `rate_limit_state` table exists (migration `0067`), suggesting partial migration to a DB-backed limiter; not all limiters use it.

### 12.5 Heavy server work

- PDF rendering: `gantt-pdf-service.ts`, `portfolio-pdf-service.ts`, `quote-pdf-service.ts`, `co-pdf-service.ts`, `estimate-pdf-service.ts`, `dot-progress-estimate-pdf-service.ts`, `sov-pdf-service.ts`, `subcontract-pdf-service.ts`, `aia-pdf-service.ts`, `logPdfService.ts` — all server-side via headless Chromium / pdfkit. Health monitors exist (`gantt-pdf-alerts.ts`, `portfolio-pdf-alerts.ts`).
- AI calls: long-running, no obvious queue. `aiNotesScheduler.ts`, `crmTaskReminderScheduler.ts`, `crmBackfillAlertDigestScheduler.ts`, `statusProbeScheduler.ts`, and `startJobRunner()` are all started in-process — autoscale would multiply schedulers across instances unless `ENABLE_SCHEDULERS` env gate is honored everywhere (mixed in code).

### 12.6 Frontend bundle

- Manual chunk splits in `vite.config.ts` for `react`, `tanstack`, `radix`, `recharts`, `konva`, `pdfjs-dist`, `xlsx`, `lucide`. Reasonable.
- Many huge components (TakeoffWorkspace 6 K LOC, etc.) ship in a single chunk. Code-splitting the takeoff workspace into smaller dynamic imports would reduce the largest chunks.
- `client/src/components/AppSidebar.tsx`, `TopHeader`, and `CommandPalette` are eager-loaded for the auth shell — fine.

## 13. Security

### 13.1 ⚠️ Highest-severity finding — committed secrets

`.replit` (committed file) contains plaintext secrets in `[userenv.shared]` (values redacted here; inspect `.replit` directly to confirm):

```
INTEGRATION_ENCRYPTION_KEY = ***REDACTED — 64-hex-char symmetric key***
VAPID_PRIVATE_KEY          = ***REDACTED — VAPID private key***
MICROSOFT_CLIENT_SECRET    = ***REDACTED — Microsoft Entra client secret***
LIVEKIT_API_KEY            = ***REDACTED — LiveKit API key***
METERED_API_KEY            = ***REDACTED — Metered API key***
```

`INTEGRATION_ENCRYPTION_KEY` is the symmetric key used by `server/integrations/encryption.ts` to encrypt every stored OAuth token in `integration_connections`. Treat as **fully compromised**: rotate and re-encrypt every stored token. The Microsoft client secret and LiveKit API key should also be rotated. Move all secrets to the Replit Secrets vault and remove them from `.replit`. Raw values are intentionally not reproduced in this audit document so that re-publication does not widen the blast radius.

### 13.2 Headers

- `helmet({ contentSecurityPolicy: …isProduction ? CSP : false })` — CSP is **disabled in dev**, enabled in prod. Production CSP is reasonable: `default-src 'self'`, `script-src 'self'` (no inline scripts), `style-src 'self' 'unsafe-inline' fonts.googleapis.com`, `connect-src` allow-list.
- `frameAncestors: 'none'` in production; `frameguard: deny`.
- `crossOriginOpenerPolicy: same-origin` in prod.

### 13.3 CORS

- Allow-listed origins from `FRONTEND_URL`, `REPLIT_DEV_DOMAIN`, `REPLIT_DOMAINS`, default `http://localhost:5173`. Credentials enabled.

### 13.4 Input validation

- Zod is widely used (655 parse calls, 121 imports), but coverage is uneven. Many `req.query.<field>` reads happen without validation.

### 13.5 SSRF

- Known open task: **"Block AI document loaders from fetching arbitrary URLs (SSRF hardening)"**. AI document fetchers should be allow-listed or run through an outbound proxy.

### 13.6 Storage / file uploads

- `server/fileValidation.ts` + `file-type` 21.3 do magic-byte sniffing.
- `server/services/safeDownload.ts` + `safeDownload-audit.md` indicate prior thinking about safe downloads.
- Multipart S3 uploads are CSRF-exempt by route shape; auth still required.

### 13.7 Object-storage tenant safety

- `server/services/storageKeyOwnership.ts` exists and is the right shape for guarding `objectKey` access. Review per-route enforcement.

### 13.8 Auth cookies

- `httpOnly`, `sameSite: lax`, `secure` in production. Token rotation via `tokenVersion`.

### 13.9 SQL injection

- All DB access goes through Drizzle's parameterized API. Direct `sql` template literal use is present (`drizzle-orm` `sql\`…\``) but uses `${}` placeholders correctly in spot-checks.

### 13.10 XSS

- `dompurify` 3.3 is installed and used in HTML-rendering paths (rich text, AI outputs). Coverage of every `dangerouslySetInnerHTML` was not exhaustively traced.

### 13.11 Multi-tenancy leakage

- See § 10.4. Known historical incident on Compliance view; no centralized enforcement.

## 16. Summary & Priority Issues

### 16.1 Overall assessment

SmartManageAI is an unusually broad and ambitious construction-management platform: ~855 K LOC of TypeScript, **532 database tables**, 174 mounted routers, 165 SPA pages, 17 third-party integration providers, an AI orchestration suite, a takeoff workspace, a CRM, payroll, hiring, vendor portals, a website builder, and a heavy-civil DOT module — all in one repository. The architecture is recognisable (Express + Drizzle + React/Vite + JWT + RBAC + Helmet/CSP + rate limiting + audit logging + CSRF), and the *intent* of the security/perf/compliance posture is right.

The dominant problem is **scale and concentration without enforced structure**:

- A single 11.5 K-line schema file holds 375 tables.
- Route handlers do their own DB calls instead of going through a thin `IStorage` layer, so cross-cutting concerns (tenancy, soft delete, audit, pagination) live in 270 separate files with no chokepoint.
- A handful of giant route files (200+ KB each) and giant React components (6 K+ LOC) make change risky.
- CSRF exemptions, raw `console.*` logging, in-memory caches, in-process schedulers, and missing pagination are all individually small but compound under autoscale.
- And one critical hygiene failure — committed plaintext secrets in `.replit` — needs to be remediated immediately.

The platform is functional and broadly working in production (per `replit.md` "Current Status: ✅ Working end-to-end" markers). Hardening, decomposition, and operational discipline are the work ahead.

Based on the documentation, here's a deep dive into why this is the most serious security risk in the platform.
What the doc says
Two relevant passages:
Connect-default app.is_superadmin='true' keeps legacy job paths working; STRICT_TENANT_RLS=true flips that off (the ratchet).
Fail-closed tenant_isolation policy with FORCE ROW LEVEL SECURITY on every multi-tenant table.
The system was designed correctly — but the ratchet is still open.
How the RLS system is supposed to work
The architecture is genuinely well-designed. Here's the intended flow:
Every authenticated request is wrapped by server/middleware/orgContext.ts in a withOrgContext() call, which binds the request to a specific org's DB client via AsyncLocalStorage (ALS). The db export is a Proxy that routes through this ALS-bound client automatically.
Every multi-tenant table has a tenant_isolation Postgres RLS policy with FORCE ROW LEVEL SECURITY — meaning even a DB superuser can't bypass it without explicitly elevating. This is the "fail-closed" guarantee.
Super admin access requires explicit runAsSuperadmin(reason, fn, { actorId? }), which writes to superadmin_access_log before elevating — and refuses if the audit write fails.
On paper, this is defense-in-depth done right.
Where the ratchet breaks it
The problem is this line in the Postgres connection setup:
app.is_superadmin = 'true'
This is a session-level Postgres variable set on every connection by default. The RLS policies almost certainly check something like:
sql
USING (
  org_id = current_setting('app.current_org_id')
  OR current_setting('app.is_superadmin') = 'true'
)
When app.is_superadmin='true' is the connect-default, every database connection bypasses the tenant filter — regardless of whether orgContext middleware is active. The RLS policies are attached and technically enforced by Postgres, but they evaluate to true for every row on every connection because the superadmin escape hatch is always open.
STRICT_TENANT_RLS=true flips that connect-default off, forcing connections to operate as normal org-scoped sessions. Until that flag is set, the entire RLS architecture is present but not doing its primary job.
What this means practically
In development and staging (where STRICT_TENANT_RLS is likely false): any bug, misconfigured middleware, or missing withOrgContext() wrapper silently succeeds instead of failing closed. You lose the ability to catch tenant isolation bugs before they reach production.
In production (if STRICT_TENANT_RLS is still false): a route that accidentally omits orgContext middleware — or a new background job that forgets withJobOrgContext() — will query across all tenants with no error. The data leak is silent. No exception, no log entry, just wrong data returned.
The 4th unwrapped job loop compounds this. The compliance-expiration job is explicitly noted as unwrapped because it "has no DB calls inside the loop body." That assumption is load-bearing. If someone adds a DB call to that loop while STRICT_TENANT_RLS=false, the query runs unscoped across all orgs — and nothing fails, nothing alerts.
The audit log for superadmin access is also undermined. If every connection is effectively superadmin by default, the superadmin_access_log only captures explicit runAsSuperadmin() calls — not the ambient bypass that's happening on every ordinary request.
Why the flag hasn't been flipped yet
The doc gives the honest answer: legacy job paths depend on it. Some background jobs were written before the org context system existed and make DB calls without going through withOrgContext(). Flipping STRICT_TENANT_RLS=true would break those jobs immediately — which is exactly what you want (it surfaces the gaps) but also requires fixing them first.
The doc says 3 of 4 job loops are wrapped. The implication is the migration is almost done, but "almost" is the problem. Until every job path is wrapped, the flag can't be safely flipped.
What should be done
Immediately: Audit every background job and scheduled task for withJobOrgContext() coverage. Create a checklist. This is the blocker for everything else.
Short term: Wrap the compliance-expiration loop proactively — even if it has no DB calls today. Adding the wrapper costs almost nothing; forgetting it later could cost a lot. The 4th loop should not remain the exception to the rule.
Before flipping the flag: Run the full test suite and smoke tests with STRICT_TENANT_RLS=true in a staging environment. Every failure is a real tenant isolation bug that would have been a silent data leak in production. Treat each failure as a critical find.
When flipping: Set STRICT_TENANT_RLS=true in production during a low-traffic window with monitoring active. Watch for any query errors that indicate an uncovered path. The system is designed to fail closed — trust that, and fix the failures.
Permanently: Add STRICT_TENANT_RLS=true to the required environment variable list alongside DATABASE_URL and SESSION_SECRET. The doc says the server fails fast on boot if SESSION_SECRET is missing — STRICT_TENANT_RLS=false should eventually be treated the same way: a misconfiguration that prevents boot, not a silent fallback.
The RLS architecture is genuinely strong. The risk isn't a design flaw — it's an incomplete migration that leaves a wide-open bypass in place. Every day STRICT_TENANT_RLS=false, the defense-in-depth is defense-in-theory.

You are a Senior Full-Stack TypeScript Engineer building an internal business app for a construction company.

==================================================
CONTEXT
==================================================
Company: TFR Construction LLC (Columbus, Ohio)
Industry: Commercial concrete subcontractor & small GC
Users: Owners, PMs, estimators, superintendents, and hourly field employees

Goal: Build a **full company management CRM + operations platform** for TFR that runs as a web app. This is NOT a toy example; it should be structured and maintainable so we can extend it later.

The app must support:
- Secure login / role-based access control
- Estimating & bid tracking
- Project management & job tracking
- Employee time card input (by day & project)
- Daily time & material (T&M) tracking
- Receipt uploading & association to projects
- Document management (plans, takeoffs, etc.)
- Per-project notes from field superintendents
- Different permissions for leadership vs hourly employees

==================================================
HIGH-LEVEL TECH REQUIREMENTS
==================================================
Use a modern full-stack TypeScript stack in THIS Repl:

- Backend:
  - Node.js + Express (or a simple TS framework) with TypeScript
  - PostgreSQL via Prisma ORM
  - REST-style API routes under `/api/*`
  - JWT authentication with httpOnly cookies
- Frontend:
  - React + TypeScript (Vite or CRA is fine, prefer Vite)
  - Component library: basic custom components (no heavy UI lib required)
  - React Router for navigation

Project structure:
- `/server` for backend (Express, Prisma, auth, API)
- `/client` for frontend (React app)
- Root `package.json` with scripts to run both dev servers or a single dev server with proxy

Environment:
- Use `.env` for DB URL, JWT secret, etc.
- Provide clear README instructions for:
  - `npm install`
  - DB migration commands
  - `npm run dev`

==================================================
USER ROLES & PERMISSIONS
==================================================
Implement role-based access control with a `role` field on the User model.

Roles:
- `ADMIN` (Owners / executive leadership)
  - Full access to everything (users, projects, estimates, timecards, receipts, T&M, plans, etc.)
- `MANAGER` (PMs, office managers)
  - Full access to projects, estimates, timecards, receipts, T&M, documents, notes
  - Can view user list but cannot change ADMINs
- `SUPERINTENDENT`
  - Can view assigned projects
  - Can upload daily notes, T&M sheets, photos, receipts
  - Can view plans and takeoffs
  - Can view time entries for their projects
- `HOURLY_EMPLOYEE`
  - Can:
    - Log their own time entries
    - View their assigned projects and project plans/documents
  - CANNOT:
    - See estimates / financials
    - See other employees’ time
    - Edit project-level data

Authentication:
- Email + password login
- Passwords hashed (e.g., bcrypt)
- Login endpoint creates a JWT stored in an httpOnly cookie
- Middleware to:
  - Attach current user to request
  - Enforce required roles per route

Seed:
- Seed one `ADMIN` user in a seed script with a known email/password for initial login.

==================================================
CORE BACKEND API ENDPOINTS
==================================================
Implement REST endpoints roughly like:

Auth:
- POST `/api/auth/login`  -> email/password, set JWT cookie, return user info
- POST `/api/auth/logout` -> clear JWT cookie
- GET `/api/auth/me`      -> return current user from JWT

Users (ADMIN-only for create/update):
- GET `/api/users` (ADMIN, MANAGER)
- POST `/api/users` (ADMIN)
- PATCH `/api/users/:id` (ADMIN)
- GET `/api/users/:id` (ADMIN, MANAGER)
- Optionally: simple “invite user” flow can be skipped for MVP

Projects:
- GET `/api/projects` (role-based filter: HOURLY only sees projects they have time entries on or are explicitly assigned to)
- POST `/api/projects` (ADMIN, MANAGER)
- GET `/api/projects/:id` (authorized roles)
- PATCH `/api/projects/:id` (ADMIN, MANAGER)
- GET `/api/projects/:id/summary` (basic stats: total hours, total receipts, etc.)

Estimates:
- GET `/api/projects/:projectId/estimates`
- POST `/api/projects/:projectId/estimates` (ADMIN, MANAGER, estimator role if we add)
- GET `/api/estimates/:id`
- PATCH `/api/estimates/:id` (ADMIN, MANAGER)

Procurement:
- GET `/api/projects/:projectId/procurement`
- POST `/api/projects/:projectId/procurement`
- PATCH `/api/procurement/:id`

Plans & Documents:
- POST `/api/projects/:projectId/documents` (file upload + metadata)
- GET `/api/projects/:projectId/documents`
- DELETE `/api/documents/:id` (ADMIN, MANAGER)

Timecards:
- POST `/api/timeentries` 
  - HOURLY can only create for themselves
  - Managers/Supers/Admins can log for any user if needed
- GET `/api/timeentries/my` (HOURLY: only own)
- GET `/api/projects/:projectId/timeentries` (MANAGER, SUPERINTENDENT, ADMIN)
- PATCH `/api/timeentries/:id/approve` (MANAGER, ADMIN)

T&M Daily:
- POST `/api/projects/:projectId/tm-dailies`
- GET `/api/projects/:projectId/tm-dailies`
- GET `/api/tm-dailies/:id`

Receipts:
- POST `/api/projects/:projectId/receipts`
- GET `/api/projects/:projectId/receipts`

Notes:
- POST `/api/projects/:projectId/notes`
- GET `/api/projects/:projectId/notes`

File Upload:
- Implement a simple local file upload (e.g., to `/uploads`) with a middleware like `multer`.
- Return `fileUrl` paths that frontend can use.
- Keep code structured so we can later swap local storage for S3 or similar.

8) Receipt Upload

9) Admin: User Management (ADMIN only)

   - Simple form to create new users (email, role, name, temp password)

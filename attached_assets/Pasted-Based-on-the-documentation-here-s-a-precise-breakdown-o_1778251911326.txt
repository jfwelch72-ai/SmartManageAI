Based on the documentation, here's a precise breakdown of why simultaneous streaming to two destinations creates a failure mode that's harder to recover from than it looks.
What the doc says
The relevant passage from the closeout architecture section:
/export which streams a ZIP via archiver with TOC PDF (pdfkit) to the client and uploads to GCS under ${PRIVATE_OBJECT_DIR}/${orgId}/closeout/
One sentence describing two simultaneous write operations to two different destinations — with no mention of error handling, atomicity, or recovery behavior for either path.
What the export operation actually does
To understand the risk, it helps to map out what's happening during a closeout export:
Step 1 — Assembly. The closeout package auto-pulls from multiple sources: warrantyDocuments, lienWaivers, projectPermits, punchListItems, projectInspections, planDocuments, and assetHandoverItems. Each of these is a separate database query, potentially fetching binary documents from GCS.
Step 2 — TOC generation. A table of contents PDF is generated via pdfkit in memory before or during archiving.
Step 3 — ZIP streaming. archiver assembles all documents into a ZIP stream. This stream is simultaneously:
•	Piped to the HTTP response for the client to download
•	Piped to GCS for persistent storage
These two destinations receive the same stream. They are not sequential — the data flows to both at the same time.
The fundamental problem with dual-destination streaming
A stream is consumed once. When you pipe a single stream to two destinations simultaneously, you're not making two independent copies — you're splitting one flow of bytes. This creates a tight coupling between two operations that have completely different failure characteristics:
Client download can fail because of: browser cancellation, network interruption, client timeout, the user closing the tab, mobile device going to sleep, or a proxy terminating the connection.
GCS upload can fail because of: GCS API errors, authentication expiry, bucket permission changes, storage quota limits, network partition between the app server and GCS, or a GCS regional outage.
These failure modes are almost completely independent. But because they share a stream, a failure in either destination affects the other.
The specific failure scenarios
Scenario 1 — GCS fails mid-stream, client has partial data.
The export starts. The client begins downloading — progress bar at 60%, 180MB of a 300MB ZIP received. GCS throws an error: a transient network partition, an authentication token expiry, a bucket quota hit. The GCS upload pipe errors.
What happens to the client download? If archiver or the HTTP response pipe doesn't handle the GCS error gracefully, the stream is destroyed — the HTTP response is terminated mid-transfer. The client receives a partial ZIP that is corrupted and unextractable. The user sees a download failure after waiting several minutes.
Worse: the client has no way to know whether the GCS copy completed or not. They may retry the export, which starts the entire assembly process again — re-querying all source documents, regenerating the TOC, re-streaming everything.
Scenario 2 — Client disconnects mid-stream, GCS has partial data.
The user starts the export, the browser begins downloading, and then the user closes the tab — accidentally, or because they switched networks, or because the download was taking too long. The client-side pipe is destroyed.
What happens to the GCS upload? If the stream destruction propagates, the GCS upload is also terminated — leaving a partial, corrupted ZIP in GCS under the expected key. The next time anyone tries to retrieve the closeout package from GCS — for audit purposes, for the client portal, for a future export — they get a corrupted file.
There's no mention of GCS upload atomicity. If GCS doesn't use a resumable upload or a write-then-rename pattern, the partial file sits at the expected path indefinitely, passing any existence check but failing any content validation.
Scenario 3 — GCS succeeds, client stream is slow, server times out.
The GCS upload completes. The client is on a slow connection, still downloading. The Express server has a request timeout — or a load balancer upstream has a connection timeout — that fires before the client finishes downloading. The HTTP response is terminated.
The client has a partial download. GCS has a complete copy. But the client doesn't know GCS has a complete copy — there's no mention of the closeout package exposing a GCS-backed download URL that the client could use to resume or retry from the stored copy.
Scenario 4 — Partial GCS write looks like success.
GCS multipart uploads can partially succeed — some parts uploaded, the final compose step fails. Depending on how the GCS client library handles this, the operation may return an error that's caught and logged, or it may return a success code for the upload initiation while the compose happens asynchronously and fails silently.
If the GCS path is later used as a "source of truth" for whether a closeout package has been generated — a database flag set to true when the path exists — a partial GCS write creates a record that says the package exists when the file is actually incomplete.
The atomicity gap
The core architectural problem is that the export operation has no atomicity guarantee across its two destinations. A truly safe dual-write operation would:
1.	Write to GCS first, completely, with verification
2.	Only begin streaming to the client after GCS confirms a complete, valid write
3.	Stream to the client from GCS via a signed URL or proxy, so the stored copy is definitively the source of truth
Instead the current approach writes to both simultaneously, which means:
•	Neither destination is guaranteed to be complete if the other fails
•	There's no canonical source of truth — GCS and the client could have different versions of the same package
•	Recovery requires knowing which destination succeeded, which isn't tracked
The closeout package's specific context makes this worse
A project closeout package is not a casual export. It contains:
•	Warranty documents with legal validity periods
•	Lien waivers that release financial claims
•	Project permits that may be required for future work on the property
•	Punch list completion records
•	Inspection sign-offs
These are legal documents assembled into a package that represents the formal close of a construction project. A corrupted or incomplete closeout package isn't just a user inconvenience — it's a potential legal liability. If a dispute arises about whether work was completed, whether a lien was waived, or whether a permit was properly closed, the integrity of the closeout package matters.
The export operation generating this package has no described integrity verification — no checksum, no completeness flag, no validation that the ZIP is extractable before it's delivered to either destination.
The GCS path as implicit state
The architecture stores the package at:
${PRIVATE_OBJECT_DIR}/${orgId}/closeout/
This path is deterministic — the same org and project will always produce the same GCS path. That means:
•	A failed export that wrote a partial file to GCS will be overwritten by the next export attempt — which is correct, but only if the next attempt succeeds
•	If a partial file exists and the next export attempt also fails mid-stream, the partial file from the first attempt is replaced by an equally partial file from the second attempt
•	There's no versioning, no archive of previous exports, no way to retrieve a known-good copy if the current GCS path contains a corrupted file
The deterministic path is convenient for retrieval but eliminates any recovery option based on previous successful exports.
What the client portal implications are
The documentation describes:
Unified External Portal (/portal): Provides a single entry point for Client, Subcontractor, and Vendor access with automatic role-based detection.
If the external client portal exposes closeout package downloads — which is a natural feature for a platform that generates formal closeout packages — it almost certainly retrieves from GCS rather than triggering a fresh export. A corrupted GCS file means every client portal download attempt for that project fails or delivers a corrupted package, with no self-healing path unless someone manually re-triggers the export and it succeeds completely.
What should be done
Decouple the two write operations. The correct pattern is sequential, not simultaneous:
1. Assemble ZIP in memory or temp storage
2. Upload to GCS completely
3. Verify GCS write (checksum, size, extractability check)
4. Only then stream to client — either from GCS via signed URL 
   or by re-reading the verified GCS copy
This makes GCS the single source of truth and ensures the client always receives a copy that has been verified as complete.
Use GCS resumable uploads. For large closeout packages, GCS resumable uploads allow an interrupted upload to be resumed rather than restarted. This is especially important given that closeout packages can be large — they contain all project documentation.
Use a write-then-rename pattern for GCS atomicity. Upload to a temporary GCS path, verify completeness, then rename (copy + delete) to the final path. This ensures the final path always contains a complete, verified file — a partial upload never overwrites a previously good copy.
Generate a signed URL for client download. Rather than streaming to the client directly from the export operation, upload to GCS first, then return a short-lived signed GCS URL to the client. The client downloads directly from GCS — bypassing the Express server entirely for the large binary transfer, eliminating server timeout risk, and giving the client a resumable download URL that GCS natively supports.
Add a completeness flag to the database. When a closeout package is successfully written to GCS, record the GCS path, file size, checksum, and a completedAt timestamp in the closeoutPackages table. Treat the absence of this record as "no valid package exists" — not a GCS path existence check.
Add integrity verification to the export. Before delivering to any destination, verify the assembled ZIP is valid and extractable. A corrupted ZIP should fail the export with a clear error rather than being delivered to either GCS or the client.
The core problem
Streaming to two destinations simultaneously trades a simple, recoverable sequential operation for a complex, partially-recoverable parallel one — to save a few seconds of latency. The client gets their download slightly faster because they don't have to wait for GCS to confirm. But the cost is a failure surface where either destination can corrupt the other's copy, neither destination is the definitive source of truth, and recovery from a mid-stream failure requires manual intervention.
For a legal document package representing the formal close of a construction project, slightly faster downloads are the wrong optimization. Guaranteed integrity is the right one.
